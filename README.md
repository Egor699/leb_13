## Ответы на контрольные вопросы

### 1. Что физически представляет собой дескриптор HMODULE, возвращаемый функцией LoadLibraryW? С какого элемента (заголовка) PE-файла начинается этот адрес в виртуальной памяти?

Дескриптор `HMODULE`, возвращаемый функцией `LoadLibraryW`, физически представляет собой базовый виртуальный адрес загруженного PE-образа DLL в адресном пространстве текущего процесса. То есть это не отдельный объект в памяти, а число-указатель на начало отображённого в ОЗУ файла библиотеки.

С адреса `HMODULE` начинается заголовок DOS — структура `IMAGE_DOS_HEADER`. Она начинается с сигнатуры `MZ` (0x4D 0x5A). Внутри этой структуры находится поле `e_lfanew`, которое содержит смещение до основного PE-заголовка `IMAGE_NT_HEADERS`, начинающегося с сигнатуры `PE\0\0`.

Таким образом, схема загрузки DLL в памяти выглядит так:

```text
HMODULE
   |
   v
IMAGE_DOS_HEADER  ("MZ")
   |
   e_lfanew
   |
   v
IMAGE_NT_HEADERS  ("PE\0\0")
   |
   v
Секции кода, данных, таблица импорта и таблица экспорта
```

### 2. Опишите низкоуровневый смысл механизма ASLR. Какую проблему безопасности ядра операционной системы решает принудительное изменение адресов загрузки DLL при каждом новом старте процесса?

ASLR (Address Space Layout Randomization) — механизм рандомизации адресного пространства процесса. Его низкоуровневый смысл заключается в том, что загрузчик Windows выбирает непредсказуемый базовый адрес для загрузки исполняемого файла или DLL вместо использования фиксированного адреса, указанного в PE-заголовке.

При включённом ASLR адрес загрузки модуля изменяется, поэтому изменяется и адрес всех функций, переменных и структур данных внутри этого модуля. Адрес конкретной функции можно представить формулой:

```text
Адрес функции = Базовый адрес модуля + Смещение функции внутри модуля
```

Смещение функции определяется содержимым DLL и остаётся постоянным, а базовый адрес модуля изменяется механизмом ASLR.

ASLR решает проблему предсказуемости памяти. Без рандомизации злоумышленник может заранее знать, по какому адресу расположены системные функции, полезные участки кода или данные. Это упрощает создание эксплойтов, использующих переполнение буфера, возврат в известный адрес кода или ROP-цепочки.

Рандомизация адресов затрудняет использование таких атак, так как атакующий не может заранее точно знать, где в памяти находится нужный ему код или данные. Однако ASLR не устраняет саму уязвимость: он лишь существенно усложняет её практическую эксплуатацию.

Важно отметить, что в Windows адреса системных DLL могут рандомизироваться не при каждом запуске отдельной программы, а при загрузке операционной системы. Поэтому при нескольких последовательных запусках скрипта адрес `user32.dll` может оставаться одинаковым до перезагрузки компьютера.

### 3. Почему функция GetProcAddress принимает имя искомой функции (MessageBoxW) строго в виде байтовой строки ASCII (b"..."), а не в виде стандартной Unicode-строки Python? Дайте объяснение с точки зрения структуры Таблицы Экспорта внутри бинарного формата исполняемых файлов PE.

Функция `GetProcAddress` принимает имя функции в виде байтовой ASCII-строки, потому что таблица экспорта PE-файла хранит имена экспортируемых функций в формате null-терминированных ASCII-строк, а не в Unicode.

Таблица экспорта DLL содержит несколько связанных структур, в том числе:

- `AddressOfFunctions` — массив адресов экспортируемых функций;
- `AddressOfNames` — массив адресов строк с именами функций;
- `AddressOfNameOrdinals` — массив порядковых номеров, связывающих имя функции с её адресом.

Имена функций в таблице экспорта хранятся как обычные последовательности байт, завершающиеся нулевым байтом. Например, имя функции `MessageBoxW` в таблице экспорта представлено так:

```text
4D 65 73 73 61 67 65 42 6F 78 57 00
M  e  s  s  a  g  e  B  o  x  W  \0
```

Поэтому в Python необходимо передавать имя именно как объект `bytes`:

```python
func_name = b"MessageBoxW"
```

Если передать обычную строку Python:

```python
func_name = "MessageBoxW"
```

то `ctypes` будет интерпретировать её как Unicode-строку UTF-16, где каждый символ занимает два байта. Такая последовательность байт не совпадёт с ASCII-именем в таблице экспорта, и `GetProcAddress` не сможет найти функцию.

Не следует путать имя функции и её аргументы. Имя `MessageBoxW` хранится в таблице экспорта в ASCII, но сама функция `MessageBoxW` принимает текстовые аргументы в формате UTF-16, так как суффикс `W` означает *Wide* — расширенную символьную строку.

Поэтому в коде используются разные типы:

```python
func_name = b"MessageBoxW"       # ASCII-имя для таблицы экспорта
text = "Сообщение"               # Unicode-строка UTF-16 для аргумента функции
```
